# DevLog — 2026-03-24
## Migração BiRefNet: ONNX → TFLite → ONNX Runtime Android

---

## Objetivo do dia

Fazer o BiRefNet-general rodar no Samsung Galaxy S22 para remoção de fundo via HTTP,
substituindo o servidor Python (CPU) por inferência no próprio smartphone.

---

## 1. Tentativa: onnx2tf (FALHOU)

**O que foi feito:**
Converter `birefnet-general.onnx` (FP32, ~1GB) para TFLite usando `onnx2tf`.

**Erro 1 — onnxsim falhou na otimização:**
```
CalledProcessError: 'onnxsim ... --overwrite-input-shape input:1,3,1024,1024' returned non-zero exit status 1
WARNING: Failed to optimize the onnx file.
```
- Não crítico — onnx2tf continuou mesmo assim.
- Fix: adicionado `--not_use_onnxsim` para pular a etapa de otimização.

**Erro 2 — op Expand quebrou a conversão:**
```
ValueError: Output tensors of a Functional model must be the output of a TensorFlow Layer. Found: 0.0
```
- O op `Expand` do BiRefNet (`/bb/layers.0/Expand`) tem uma entrada constante que
  se resolve para `0.0`, e o onnx2tf não consegue encapsulá-la como Keras Layer.
- O BiRefNet tem 360 ops `Expand` no total.
- **Conclusão: onnx2tf não suporta BiRefNet. Abandonado.**

---

## 2. Decisão: Trocar TFLite por ONNX Runtime Android

**Por que ORT:**
- Roda `.onnx` diretamente, sem conversão de formato.
- Suporta NNAPI EP (NPU/GPU/DSP) nativamente via `addNnapi()`.
- Evita todos os problemas de conversão de ops.

**Mudanças realizadas:**

### `scripts/convert_rmbg14.py`
- Removida toda a lógica onnx2tf.
- Adicionada conversão FP32 → FP16 com `onnxconverter-common` (`keep_io_types=True`).
- Output: `birefnet-general-fp16.onnx` (~467–490MB).

### `app/build.gradle`
- Adicionado: `com.microsoft.onnxruntime:onnxruntime-android:1.17.3`
- `noCompress "onnx"` nos aaptOptions.

### `ModelRunners.kt` — `BackgroundRemover`
- Reescrito completamente para usar `OrtEnvironment` + `OrtSession`.
- Preprocessing mudou de **NHWC → NCHW** (formato nativo PyTorch/ONNX).
- NNAPI habilitado em API 27+, fallback para CPU em API 26.
- Acelerador escolhido automaticamente.

## 3. Erros encontrados na integração Android

### OOM no `readBytes()` — RESOLVIDO
```
OutOfMemoryError: Failed to allocate a 490080536 byte allocation with 41666736 free bytes
```
- `context.assets.open(...).readBytes()` tentava alocar 490MB no heap Java (limite ~512MB).
- **Fix:** copiar para `filesDir` uma vez e usar `createSession(filePath)` — ORT faz `mmap`
  nativo, fora do heap Java completamente.

### APK com integer overflow no build — RESOLVIDO
```
Execution failed for task ':app:packageDebug' > integer overflow
```
- APK excedia 2GB com o modelo de 490MB nos assets.
- **Fix:** `ignoreAssetsPattern "birefnet-general-fp16.onnx"` no `aaptOptions`.
  Modelo excluído do APK e enviado separadamente para o device.

### `adb push` com Permission Denied — RESOLVIDO
```
cp: /data/data/com.aidetector/files/...: Permission denied
```
- `adb shell run-as` falha em Samsung com SELinux restritivo.
- `/sdcard/Android/data/<pkg>/files/` não acessível via adb no Android 11+.
- **Fix:** endpoint HTTP no próprio app (`POST /api/v1/models/upload`) que recebe
  o arquivo via `curl` e salva direto no `filesDir`.

```bash
curl -X POST http://192.168.3.13:8080/api/v1/models/upload \
  -F "file=@/caminho/modelo.onnx" \
  -F "name=birefnet-general-fp16.onnx"
```

### Cast errado no ORT output — RESOLVIDO
```
ClassCastException: results[0].value as OnnxTensor
```
- `results[0]` retorna `OnnxValue`. `.value` retorna o objeto Java (array), não o tensor.
- **Fix:** `results.get(0) as OnnxTensor` — cast direto no `OnnxValue`.

### `addNnapi()` pode quebrar na criação da sessão — RESOLVIDO
- Se o NNAPI não suportar algum op, a exceção explode em `createSession()`.
- **Fix:** try-catch com fallback automático para CPU.

### Timeout HTTP (5s → 30s) — RESOLVIDO
- `ai_client.py` usa `timeout=30` por padrão. BiRefNet leva mais.
- **Fix:** método `remove_background()` com `timeout=120` próprio.
- `app.py` (Flask) atualizado para usar o novo método e o model default correto
  (`onnx/birefnet-general-fp16.onnx` em vez de `rmbg2.tflite`).

### Warmup adicionado no `initialize()`
- NNAPI compila o grafo na primeira inferência, causando timeout na primeira requisição real.
- **Fix:** inferência dummy com `FloatBuffer` zerado logo após `createSession()`.

### `OutOfMemoryError` não capturado pelo NanoHTTPD — RESOLVIDO
- `OutOfMemoryError` é um `Error`, não `Exception`. O catch existente não o pegava,
  causando disconnect no cliente sem mensagem de erro.
- **Fix:** catch separado para `OutOfMemoryError` + `Throwable` no `serve()`.

## 4. Tentativa: onnxsim para redimensionar para 512×512 (FALHOU)

**Motivação:** inferência em 1024×1024 pode OOM. 512×512 = 4× menos memória.

**Erro 1 — nome errado:**
```
RuntimeError: The model doesn't have input named "input"
```
- O input do BiRefNet se chama `input_image`, não `input`.

**Erro 2 — modelo quebrado após resize:**
```
ORT_FAIL: Node (/bb/patch_embed/Reshape_1) Op (Reshape) [ShapeInferenceError]
Dimension could not be inferred: incompatible shapes
```
- O Swin Transformer backbone usa `Reshape` ops que dependem das dimensões exatas do input
  (cálculo de patches: 1024/4 = 256 patches → vira constante no grafo).
- onnxsim constant-fold essas dimensões durante a simplificação, e elas ficam
  incompatíveis com o novo tamanho.
- **Conclusão: não é possível redimensionar BiRefNet com onnxsim. Requer re-export
  do PyTorch com o tamanho desejado.**

## 6. Tentativa: INT8 quantization (FALHOU — modelo ficou maior)

**Motivação:** FP16 causa OOM na inferência. INT8 deveria usar ~50% menos memória.

**Método:** `onnxruntime.quantization.quantize_dynamic` com `QUInt8`.

**Resultado:**
```
FP32 original:  927 MB
INT8 gerado:   1044 MB  ← maior que o FP32!
```

**Por que ficou maior:** a quantização dinâmica do ONNX adiciona nós
`QuantizeLinear`/`DequantizeLinear` em torno de cada op quantizado.
Em modelos transformer como BiRefNet (com centenas de MatMul e atenção),
o overhead desses nós supera o ganho da compressão de pesos.

**Conclusão:** INT8 dinâmico não é viável para BiRefNet no formato ONNX.
A alternativa seria quantização estática com calibration data + exportação
direto do PyTorch com `torch.ao.quantization`, que está fora do escopo.

## 7. Decisão final: reverter para RMBG-1.4 TFLite

**BiRefNet é inviável para inferência Android** com as ferramentas disponíveis:
- onnx2tf: falha no op Expand
- FP16 ONNX: OOM confirmado pelo lowmemorykiller no S22
- onnxsim resize: quebra o modelo (Reshape incompatível no patch_embed)
- INT8 dinâmico: modelo fica maior que FP32

**Solução:** voltar para `rmbg2.tflite` (BRIA RMBG-1.4, 176MB) que já estava
nos assets e funcionava antes de toda a migração.

**Vantagens do rmbg2.tflite:**
- Já incluso no APK (sem upload necessário)
- TFLite com NPU/GPU via DelegateFactory existente
- 176MB vs 490MB — cabe confortavelmente em memória
- Inferência testada e funcional

**BackgroundRemover:** revertido para a implementação TFLite original (NHWC, DelegateFactory).
ORT Android e imports removidos do arquivo.

**Confirmação do OOM via logcat:**
```
lowmemorykiller: process_mrelease 10592 failed  (8+ processos mortos em ~2s)
```
O lowmemorykiller disparou em cascata durante a inferência BiRefNet FP16,
confirmando pressão severa de memória.

## 8. Debug e fix do rmbg2.tflite — RESOLVIDO

Após reverter para TFLite, o rembg retornava imagem completamente transparente.
Debug via logcat revelou três bugs no preprocessing:

```
Output tensor: shape=[1, 512, 512, 1] dtype=FLOAT32
Mask sigmoid: min=3.4028235E38 max=1.4E-45  ← NaN em todos os pixels
```

**Bug 1 — INPUT_SIZE errado (1024 → 512):**
O modelo aceita 512×512. `512×512×3×4 = 3.145.728 bytes` (float32).
A mensagem de erro anterior "cannot copy 3145728 bytes from 12582912" era
float32 512×512 vs float32 1024×1024, não uint8 vs float32 como assumimos.

**Bug 2 — uint8 em vez de float32:**
Corrigido. Modelo espera float32.

**Bug 3 — normalização errada (ImageNet → RMBG-1.4):**
O rembg normaliza RMBG-1.4 com `mean=0.5, std=1.0` → `(pixel/255 - 0.5)`.
Usar ImageNet stats `(0.485, 0.456, 0.406) / (0.229, 0.224, 0.225)` gerava
valores fora do range esperado → ativações com overflow → NaN → máscara vazia.

Com a normalização correta:
```
Mask sigmoid: min=0.12 max=0.94 range=0.82  ← segmentação correta
```

**Resultado final: rembg funcionando no S22 com NNAPI em ~1.4s por imagem.**
